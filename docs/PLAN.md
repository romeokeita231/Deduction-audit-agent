# 范围与里程碑

一个单人、业余时间的作品集项目。这份文件说明它做了什么、**故意没做什么**、为什么，以及怎么验证它确实做到了。

每一个"不做"都是判断，不是遗漏——所以第 3 节比第 2 节值得读。

## 1. 成功标准

1. `docker compose up -d` + `mvn spring-boot:run` 之后，浏览器能打开队列页并看到带倒计时的扣款列表。
2. 一条扣款从 `POST /evaluate` 到状态进 `AWAITING_ACTION`：**p95 ≤ 30 秒、硬截止 45 秒**（均含重试），且每个工具调用的入参/出参/耗时都能在详情页上看到。
3. 评估管线以 fixture 形式进 CI（< 2 分钟，**不调模型**）；真打 100 条模型的 `eval:live` 产出可存档的报告，不阻塞 merge（[ADR 0007](./adr/0007-ci-runs-pipeline-not-model.md)）。
4. 能在 90 秒内讲清"为什么这是 Agent，而不是 RAG 问答"。
5. `docs/QA.md` 覆盖 20 个设计追问（"为什么不用 Redis""为什么只做三类扣款"……），每个都有书面答案。

## 2. 范围之内

- **三类扣款**：缺货/货损、价格差异、促销。每类对应一种互不重复的推理机制。
- **两种存储**：PostgreSQL 16 + pgvector（业务 + 向量）、MongoDB（原始凭证 + Agent 轨迹）。
- **单一角色 AR**：不做鉴权，也不做角色切换。
- **两页 Web UI**：队列页、详情页（Thymeleaf）。
- **评估**：冲突矩阵生成的约 100 条合成数据 + Python harness。
- **CI**：编译与单测、fixture 评估、失败即红。
- **MCP**：stretch——把工具注册成 MCP Server，用客户端连一次并录进视频。

## 3. 范围之外

| 不做 | 为什么 |
|---|---|
| 合规物流类、行政审计类扣款 | 前者与缺货类共用同一批物流单据，机制重复；后者的查重本质是一条 SQL，模型没有戏份 |
| Elasticsearch | pgvector 在同一个事务里就给了向量检索；ES 镜像 921MB、单机建议 4GB，还要多背一个一致性边界 |
| Redis | 幂等锁必须与业务写入同事务。PG 的唯一索引 + advisory lock 做得到，Redis 做不到——多一个组件换来一个一致性 bug |
| 微服务、消息队列 | 这里要证明的是"能设计边界"，不是"能起很多进程"；单人项目拆服务只会把调试成本乘以进程数 |
| 跨类发现（在缺货单里查出促销问题） | 要每类挂上全部工具，工具选择错误率上升，结论会变成需要仲裁的复合结构。故事好听，但做不深 |
| 真实 EDI / 零售商 API 对接 | 全部合成数据，见第 8 节 |
| React 前端 | 一个可部署单元优先。前后端分离在这里只多一个构建链和一个跨域问题，不多一分说服力 |
| 真鉴权、多租户、Evaluator-Optimizer | 没有可验证的收益，只会稀释注意力 |
| LLM 参与路由 / 分类 | 分类是可运维的映射表。加模型兜底会让"分类不是一次模型调用"这句话自相矛盾，也会让演示路径和评估路径分叉 |
| Ops 角色 | 合规物流类砍掉之后，13 条转移里 Ops 有 0 条权限。没有权限的角色只是一个下拉框 |
| 第二个业务场景（FBA 理赔） | 一次只做一个场景才能把取舍讲透；第二个场景用一张对照表保留，不用第二套代码 |

## 5. 评估设计

**数据**：冲突矩阵。三类扣款 × 五种证据情形，每格 6–7 条，约 100 条：

| 证据情形 | 正确答案 | 这一格测什么 |
|---|---|---|
| 齐全且支持 Supplier | `DISPUTABLE` | 能不能把三份证据装对 |
| 齐全但支持 Retailer | `DEDUCTION_STANDS` | 会不会为了"想赢"而扭曲读数 |
| 证据缺失 | `INCONCLUSIVE` + 非空 `missingEvidence` | 敢不敢说不知道 |
| 自相矛盾·有规则可裁 | 按政策优先级裁定 | 会不会按规则选证据，而不是取平均 |
| 自相矛盾·无规则可裁 | `INCONCLUSIVE` + 空 `missingEvidence` | 会不会在规则空白处硬编一个理由 |

**标注用四态**：扣款成立 / 可争议 / 证据不足·缺证据 / 证据不足·无规则。**不要用 valid / invalid**——它没说清"对谁有效"，一旦进了标注表，准确率就没有意义了。三态会把矩阵第 3 行（证据缺失）与第 5 行（无规则可裁）合并成一个"证据不足"，于是对无规则 case 硬报"缺证据"也判对——正是本节最后警告的那一格被做假。成因的区分见 [ADR 0009](./adr/0009-evaluation-corpus-and-metrics.md)。

**规则与答案的边界**（[ADR 0004](./adr/0004-rules-in-context-answers-never.md)）：政策规则**进** system prompt——"POD 决定收货量、BOL 决定发货量、价格以生效区间为准"本来就是书面政策，不给它就是让人猜。**oracle 的判定结果永不进 prompt。**

**oracle 是代码，M6 开工前冻结。** 此后不得因为看了 Agent 的输出而调整规则或标注。这条不写死，前面所有指标都可以在事后被调松。

**指标**（从硬到软）：

1. **Verdict agreement**：与冻结后的 oracle 比对，报总体准确率 + 每类召回率。
2. **Evidence citation precision / recall**：只在 `claim.supportingEvidence` 上算，不解析散文；引用必须是封闭集（[ADR 0005](./adr/0005-evidence-ids-from-natural-keys.md)），越界直接判失败。
3. **文书结构完整率**（确定性）：**头条**是产出的文书中骨架齐备、词数在界内的占比——分母只含实际产出的文书，守住"这个数只反映管线"。**并列第二个数叫产出率** = 实际产文书数 / oracle 判 `DISPUTABLE` 的条数，让"该产没产"可见。两个数永不相乘。骨架按字符偏移的先后判（金额在前、证据 ID 居中、诉求在后、收尾在最后），与段数无关——契约允许 3–5 段，按段索引会系统性压分。写入时的五条硬校验是门不是比率：违反的文书根本不会落库，由集成测试守。原"文书可用率"（LLM judge）降为人工抽检的观察项，输入口径固定为 `claim` + `narrative` + `digest` 三元组，不给自动闸门。

**这套指标测的是政策执行力，不是判断力。** README 必须这么写——否则"95% 准确率"会被读成"它会像人一样判断"。真正的判断只在"无规则可裁"那半格被测量（约 20 条，正确答案是 `INCONCLUSIVE`），而那也正是最容易被做假的一格。

**Holdout**：只在促销类内部做——检索回来的某份协议里，结算口径与 prompt 里给的不一致，看 Agent 会不会以文档为准。不做成"跨类发现"：缺货类的 Validator 手上没有促销工具，测不到，测了也是假阳性。**Holdout 延后至 M7，且永远是人工跑 `eval:live` 时的观察项，不进 CI 闸门**——它判的是"以文档为准"，属于语义判定，而 CI 里没有真模型（[ADR 0007](./adr/0007-ci-runs-pipeline-not-model.md)）。

## 6. 风险

| 风险 | 对策 |
|---|---|
| 脚手架吃掉全部时间 | M0 只许做一件事：让模型调通一个 `@Tool`。不通过不进入 M1 |
| Spring AI 2.0 资料少、API 新 | API 用法一律对着官方文档核，不凭记忆写；每个里程碑先跑最小样例 |
| 范围蔓延 | 第 3 节是硬边界，新增任何一项必须删掉同等工时的另一项 |
| 评估自欺 | oracle 与 prompt 分离；指标 2 必须能独立复算 |
| Docker 首次使用的挫败 | 先只起 PG 一个容器，跑通了再加 Mongo |

## 8. 诚信边界

README 必须写明：业务规则与数字来自公开行业资料，数据为合成，作者无 CPG 从业经验。这一条不写，整个项目的可信度归零。

另外两句是同一件事的三面，也必须出现在 README：

- **指标测的是政策执行力，不是判断力**（ADR 0004）。
- **CI 绿灯只代表管线正确，不代表模型没退化**（ADR 0007）。
