# 扣款是事件，不是状态

Status: accepted

零售商可以对同一个 PO 反复扣款，每次扣款都是一次独立动作；争议窗口从**各自的扣款日**起算，而不是从 PO 或发票起算。因此我们把每一笔 Deduction 建模为不可变的行项目（聚合根），后续的金额调整以新增一条 adjustment 记录表达，绝不就地修改原记录；Dispute 以 0..1 挂在 Deduction 下，关闭后不可改写。幂等键和 SLA 计时都以 `deduction_id` 为粒度。

如果按 PO 或批次聚合，UI 会简单一点，但窗口算错、审计链断掉，且已发出的争议文书会因为源数据被改写而失真。

## Consequences

- "某 PO 的扣款总额"变成派生值，不再是字段，需要聚合查询。
- 同一 PO 的多次扣款在队列页上要分组展示，否则看起来像重复数据。
- 修正历史错误只能靠追加，不能靠覆盖——这会让演示数据里出现"负金额"记录，需要提前在 UI 上解释。
